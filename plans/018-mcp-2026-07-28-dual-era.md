# Plan 018: MCP 2026-07-28 dual-era modernization

Status: shipped (2026-08-07) — see "Shipped: verification evidence" below
Baseline: `main` @ `69df6f278bf5f3047fd003eb9a4da5401b2110d9`, clean tree,
`swift test` green (146 tests, 0 failures) before any edits.

## Phase 1 audit

### Current architecture (evidence)

- Swift 6.x server, MCP swift-sdk pinned `0.12.1` (`swift/Package.resolved`),
  which targets spec **2025-11-25**. No swift-sdk release supports
  2026-07-28 (latest tag 0.12.1, 2026-04-29; the official 2026-07-28 SDK
  betas cover Python/TypeScript/Go/C# only). The modern era therefore must
  be implemented as a **repo-level adapter**, not an SDK upgrade.
- Transports: stdio (SDK `Server` + `StdioTransport`, wrapped by
  `IconMetadataTransport`) and hand-rolled Streamable HTTP
  (`HTTPTransport.swift`, Hummingbird 2.x) implementing the legacy
  session-based shape: `initialize` → `Mcp-Session-Id`, GET SSE, DELETE,
  supported versions 2024-11-05 … 2025-11-25.
- Tools: 12, registered into a global `ToolHandlerRegistry` (process-wide,
  session-independent — already effectively stateless). Capabilities:
  `tools.listChanged: false`. No prompts, resources, subscriptions,
  sampling, roots, MCP logging, elicitation (intentionally removed, plan
  017), or tasks.
- Ordering bug for the new spec: `ToolHandlerRegistry.getTools()` returns
  `Array(tools.values)` — nondeterministic dictionary order.

### Real clients (must not regress)

| Client | Transport | Era | Evidence |
| --- | --- | --- | --- |
| plug (primary; all MCP routed through it) | Streamable HTTP `http://127.0.0.1:8080` | **legacy** (`protocol = "legacy"` in `~/Library/Application Support/plug/config.toml` `[servers.imessage]`) | config read 2026-08-07 |
| mcpb bundle (Claude-Desktop-style) | stdio binary | legacy `initialize` | `mcpb/manifest.json` |
| Codex Desktop / MCP Inspector | stdio / HTTP | legacy | AGENTS.md |

No known consumer speaks 2026-07-28 today ⇒ the legacy lane is load-bearing
and is preserved verbatim; the modern lane is added beside it (dual-era
server, explicitly permitted: "A dual-era server MAY serve both eras
concurrently on the same endpoint or process").

### Requirements matrix vs 2026-07-28 (primary sources: spec pages
`basic/index`, `basic/versioning`, `basic/transports/streamable-http`,
`basic/transports/stdio`, `server/discover`, `changelog`)

Required, to implement (modern lane):
- `server/discover` (MUST): supportedVersions, capabilities, instructions,
  `_meta` serverInfo, ttlMs/cacheScope.
- Per-request `_meta`: `io.modelcontextprotocol/protocolVersion` (required)
  and `clientCapabilities` (required) → missing = `-32602` (HTTP 400);
  unsupported version = `UnsupportedProtocolVersionError` `-32022` with
  `data.supported`/`data.requested` (HTTP 400).
- `resultType: "complete"` on every modern result; serverInfo in result
  `_meta` (SHOULD).
- Stateless modern execution: no initialize, no session. Tool state is
  already carried by explicit ids (chat ids, attachment ids) as ordinary
  arguments — matches SEP-2567 handle model.
- HTTP modern lane: `MCP-Protocol-Version` + `Mcp-Method` required on every
  request POST, `Mcp-Name` on `tools/call`; header/body mismatch or missing
  header = `-32020` HeaderMismatch (HTTP 400) with Base64 sentinel decoding
  for `Mcp-Name`; unknown method = `-32601` (HTTP 404); notifications =
  202; single JSON responses (no SSE needed — server emits no
  request-scoped notifications); Origin validation already enforced by
  middleware; loopback-only binding preserved.
- `tools/list`: deterministic order (registration order) + required
  `ttlMs`/`cacheScope` (CacheableResult) on the modern lane.
- stdio modern lane: same dispatcher, era selected per message
  (`server/discover` or modern `_meta` ⇒ modern; everything else ⇒ legacy
  SDK server), newline-framed stdout only, logs on stderr (already true).
- Observability: stderr line per modern-era decision (transport, era,
  version, method, clientInfo) with no arguments/credentials.

Already compliant (no change):
- Legacy lane behavior for 2024-11-05…2025-11-25 (kept for real clients).
- Origin/Host validation (DNS-rebinding), loopback default bind.
- JSON Schema: plain 2020-12-compatible object schemas; no `$ref`, no
  composition keywords ⇒ bounded-processing requirements trivially met.
- Protocol vs tool-execution error separation (`ToolError` → `isError`).
- stdio framing/stderr discipline.

Not applicable (with reasons, per rule 5):
- **subscriptions/listen**: server never emits change notifications
  (`tools.listChanged: false`, static tool catalog per build; no
  resources/prompts). Unknown method → `-32601` is the compliant answer.
- **MRTR / InputRequiredResult**: no sampling, roots, or elicitation —
  elicitation is intentionally excluded from the send path (plan 017;
  AGENTS.md forbids reintroduction without operator sign-off). All tools
  complete in a single round trip.
- **requestState integrity/expiry**: no MRTR ⇒ no requestState.
- **Tasks extension**: no durable long-running work; every tool returns
  synchronously in seconds.
- **MCP Apps**: no embedded UI product surface.
- **OAuth authorization**: HTTP transport is loopback-only by policy
  (`HostBindingPolicy`), single-user local data; spec's remote
  authorization framework targets network-exposed servers. stdio-style
  credential posture applies: access is governed by macOS TCC grants (Full
  Disk Access, Contacts, Automation), not tokens; no secrets in env.
- **Deprecated features (Roots/Sampling/Logging/HTTP+SSE/includeContext/
  DCR)**: never used; nothing to migrate.
- **x-mcp-header**: optional for servers; no parameter benefits from
  intermediary routing on a loopback server.
- **prompts/resources catalogs + cache hints**: features not implemented.

Deliberate dual-era compatibility note: the legacy HTTP GET/DELETE/session
surface is retained (it would be 405 on a modern-only server) because real
legacy clients depend on it; this is the documented dual-era exception.

Known limitation (documented, accepted): modern-lane HTTP cancellation via
response-stream closure is best-effort — responses are single JSON bodies
for fast, read-mostly tools; a disconnected client's tool call runs to
completion and the response is discarded. `send` retains its verified-send
contract; duplicate retry of `send` can double-send (same as legacy;
harness-level approval is the guard).

## Phase 2 staged plan (dependency order)

1. **Deterministic catalog**: registration-ordered `getTools()` (+ test).
   Benefits both eras.
2. **Modern core adapter** `ModernProtocol.swift`: version table, era
   detection, `_meta` validation, `server/discover`, `tools/list` (+cache
   hints), `tools/call`, error mapping (−32601/−32602/−32020/−32022),
   `resultType`, serverInfo `_meta`, era observability line (+ unit tests,
   incl. negative).
3. **HTTP era routing**: branch in `handlePost` before legacy validation;
   modern header validation (Mcp-Method/Mcp-Name/MCP-Protocol-Version,
   Base64 sentinel, notification 202, 404 −32601) (+ integration tests,
   legacy tests untouched and green).
4. **stdio dual-era**: `DualEraStdioTransport` intercepting modern messages
   ahead of the SDK server; legacy passthrough incl. icon injection
   (+ tests).
5. **Docs**: README + AGENTS updates (supported eras/transports, N/A
   features, rollback), this plan updated to "shipped".
6. **Verification**: full `swift test`; `make install`; live probes of the
   installed service (legacy initialize flow, modern discover/tools/call,
   negative cases) over HTTP :8080 and stdio; official conformance suite
   (`modelcontextprotocol/conformance`) against the modern lane; confirm
   plug still healthy on the legacy lane.

Rollback: single revert of the migration commits restores the pre-018 wire
behavior; the legacy lane is untouched throughout, so rollback risk is
confined to the new modern branch and the tools/list ordering change.

Out of scope without explicit authorization: switching plug's
`[servers.imessage]` to the modern protocol, publishing/pushing, removing
any legacy behavior.

## Shipped: verification evidence (2026-08-07)

Implementation landed as: `ModernProtocol.swift` (stateless 2026-07-28
dispatcher), `DualEraStdioTransport.swift` (stdio era router),
era branch + header validation in `HTTPTransport.swift`, deterministic
tools/list ordering in `ServerExtensions.swift`, catalog pre-registration
fix (`ensureToolCatalogRegistered`), version bump 1.2.1 → 1.3.0
(Version.swift, mcpb/manifest.json, .codex-plugin/plugin.json).

- `swift test`: 174/174 pass (146 baseline + 28 new: ModernDispatcherTests,
  ModernHTTPIntegrationTests, DualEraStdioTransportTests).
- Official conformance suite (modelcontextprotocol/conformance
  v0.2.0-alpha.10) against the installed service on 127.0.0.1:8080:
  `--suite draft` (2026-07-28) exit 0 — 58 checks pass; `--suite active`
  (legacy) exit 0 — 39 checks pass. All baselined failures are documented
  N/A features or suite-diagnostic-tool scenarios
  (`docs/conformance-baseline.yml`); wire-schema checks pass everywhere;
  http-header-validation 14/14.
- Intentional deviation: `initialize` is served by the legacy lane rather
  than 404ing (dual-era requirement; stateless-only servers would 404).
- Live probes of the installed 1.3.0 artifact: modern
  discover/tools-list/tools-call + all negative cases (-32020/-32022/
  -32601/-32602, 202 notifications, sentinel Mcp-Name) over HTTP; modern
  discover/tools-list/tools-call and legacy initialize over stdio.
- Real-client regression found and fixed during verification: plug sends
  `Mcp-Method`/`MCP-Protocol-Version` headers on legacy session traffic;
  header-based era detection misrouted it to the modern lane. Era selection
  is now body-only (`ModernDispatcher.isModernMessage`). Regression test:
  `testLegacyRequestWithModernHeadersStaysOnLegacyLane`.
- plug (primary client, HTTP legacy) verified end-to-end post-install:
  `diagnose` through plug returns status ready on version 1.3.0.
- Not exercised: Codex Desktop / Inspector GUI reconnect (manual step;
  same legacy lane plug uses). plug remains on `protocol = "legacy"` —
  switching it to modern stays out of scope without authorization.

### Direction items recorded as operator options (not planned)

Surfaced by the audit as product directions rather than defects. Each is a
small design decision the operator can turn into a `plan <description>`
invocation when wanted:

- **Richer message semantics** in `get_messages`/`search` responses: expose reactions (tapbacks), replies-to, edits, and unsent markers as structured fields instead of leaving them for the client to infer from `associated_message_type`. Evidence: the raw columns are already selected; only the mapping is missing.
- **`get_changes_since` cursor tool**: a single "what happened since cursor X" tool for polling agents, built on `TimelineCursor`. Would replace the `get_unread` + `get_active_conversations` polling pattern.
- **`doctor` / `install-service` subcommands** on the binary: move the Makefile's `verify`/`status`/`install-agent` logic into the executable so Homebrew users get it without the repo.
- **Outbound `file_paths` containment** for `send`: restrict attachment sources to an allow-list of directories the way `AttachmentPathPolicy` already restricts inbound reads. A security posture choice; today any readable path can be sent by an agent.
- **Output schemas: fill or drop.** Eleven tools register `OutputSchema.object` (`{"type": "object"}`) which tells clients nothing; `get_attachment` registers none. Either author real schemas per tool or drop the placeholder so clients do not assume validation.
- **Per-tool call stats** on `diagnose` (counts, p50/p95 latency): cheap to add once plan 051's query counter exists; useful for spotting the next hot path.

### Findings considered and rejected (2026-09-01)

- **Makefile `add-trusted-cert`** adds the local signing certificate to the login keychain trust settings. Flagged as a security risk; it is the documented one-time setup for the persistent signing identity (plans 036/037) and runs only when the operator invokes it. By design.
- **CI cache `restore-keys` poisoning.** Flagged that a partial-key restore could load a stale `.build`. SwiftPM validates the build graph against `Package.resolved`; a stale cache is a slower build, not a wrong one. Wrong mechanism.
- **Top-level-array `structuredContent`.** `structuredValue(from:)` would mis-wrap a response whose root is an array. No tool returns a root array; latent, not live. Revisit if a tool ever does.
- **`SendVerifier` 800 ms poll interval.** Flagged as latency. It is the product tradeoff between send confirmation speed and Messages.app load, chosen in plan 012 with measurements. Not a defect.
- **swift-sdk migration.** Upstream is stalled at 0.12.1 with no successor; there is nothing to migrate to. Plan 048 pins it instead.
- **FTS5 sidecar index for search.** A separate full-text index over chat.db would need a sync process and a second database to keep consistent. Plan 045's SQL prefilter plus the bounded scan is the right size for this product.
- **Removing the deprecated `confirm` parameter.** Documented as deprecated-but-accepted by plan 017's agent-native send contract; removing it breaks older client prompts for no gain.
- **Swift Testing migration.** 278 XCTest tests with `XCTExpectFailure`, `measure`, and fixture patterns that have no direct Swift Testing equivalent. Cost without a benefit the project feels.
- **Homebrew Formula "lagging" at v1.4.1.** v1.4.2 was bumped in source but never tagged or released, so the Formula is correct. Plan 052 adds the check that would have made this obvious.

#### The SSE happy path needed a different client, not a different endpoint

038's plan flagged one test as genuinely uncertain: asserting a 200 on a
streaming endpoint through `HummingbirdTesting`. It hung, permanently, not
slowly. `RouterTestFramework.swift:122` runs

constructing the `TestResponse`, and `handleGet`'s body pumps SSE keep-alives

body-collecting client.

endpoint.** The first executor's instinct, quarantine the test and escalate,
was correct given its instructions, and the plan's STOP condition is what made
that the safe move rather than a silent timeout hack.

## Release v1.4.0 (2026-08-07)

Tagged at `da91fbc`, published at
<https://github.com/cyberpapiii/imessage-max/releases/tag/v1.4.0>.

**Why 1.4.0 and not 1.3.0.** `Version.swift` had said `1.3.0` since the
dual-era MCP work, but no v1.3.0 tag or release ever existed, the latest
published release was v1.2.1. Shipping 21 additional plans under a number the
tree had already been carrying would have been misleading, so the version
moved forward. Minor, not major: the new send statuses (`failed_delivery`,
`partial_failure`) are additive and nothing in the tool surface broke.

The version lives in **four** places, all bumped together, miss one and they
drift silently:

- `swift/Sources/iMessageMax/Server/Version.swift`
- `mcpb/manifest.json`
- `.codex-plugin/plugin.json`
- `swift/Formula/imessage-max.rb` (the release-asset URL)

`swift/Package.swift` also contains the string `1.3.0`; that is
swift-argument-parser's minimum version and must not be touched.

**The Formula sha256 is real now**, replacing the zero placeholder:
`e2b123cbede36315a0762f15bee3a51ded6c3252ad9c2cb5361594acbb2cc333`. Verified
by downloading the published asset and re-hashing it, not by trusting the
local file.

**The published asset is ad-hoc signed, deliberately.** The local binary is
signed with the `iMessage Max Dev` identity, which is what makes Full Disk
Access persist across rebuilds (plan 037), but that identity is self-signed
and exists only in this machine's keychain, so a downloaded binary carrying it
would present an untrusted authority anywhere else. The release tarball is
built from a separate copy re-signed with `codesign --sign -`. **Anyone
rebuilding the asset must repeat that step**, or `brew install` ships a binary
signed by an authority the installing machine has never heard of.

**Deploy confirmed.** `make sign` used the persistent identity
(`F9E455A3BB848F2623DA215A224E7F826B09C4BC`), the service restarted, and both
lanes reported healthy at v1.4.0. Most importantly, `diagnose` came back with
`perm_full_disk: supported` and `database.accessible: true` **without any GUI
re-grant**, the first re-sign since 037 landed, and the empirical proof that
the fix works. Every prior deploy revoked FDA and required re-granting it by
hand.

## Deferred / rejected in the 2026-08-07 audit

Recorded so future audits don't re-litigate:

- **DB connection pooling / per-tool `Database()` instances** (PERF): real
  but unmeasured; every tool opens read-only SQLite connections that are
  cheap on local disk. Measure before building a pool, no plan until
  latency is demonstrated.
- **`send` `file_paths` containment** (SECURITY): `validateFilePath` checks
  existence/readability but not location, so an agent can send any readable
  file (e.g. `~/.ssh/id_rsa`) out via iMessage. Deliberately NOT planned:
  legitimate use includes sending arbitrary user files; a containment
  policy here is a product decision (allowlist? size cap? prompt?), not a
  bug fix. Operator to decide; revisit as a direction item.
- **MCP swift-sdk migration off the hand-rolled modern lane** (DEPS): no SDK
  release supports MCP 2026-07-28 yet, there is nothing to migrate to.
  Plan 027's matrix is the acceptance suite when that day comes.
- **Sidecar FTS index for search** (DIRECTION): stays rejected (see the
  2026-06-11 rationale below); still no reported search-latency pain.
- **Direction features surfaced but not selected** (operator chose "none for
  now", 2026-08-07): tapbacks/replies support, edit/unsend visibility, live
  inbox (push-style unread streaming). Grounded in schema evidence; park
  until requested.

### Elicitation: resolved (was "open direction", now closed by 017)

The 2026-06-11 live debugging established that the interactive send-
confirmation elicitation **never completed a round trip** in the plug client
stack: pre-014 it hung until the client's 300s transport timeout; 014's
bounded wait used a Task.sleep timer that crashed the launchd service
(reproduced live, exit status 6, fixed by 015); post-015 it degraded to
`pending_confirmation` after ~25s. Plan 017 resolved the direction question
by **removing the elicitation wait entirely**, sends verify passively
against chat.db (bounded polling, no client interaction), and AGENTS.md now
codifies "no confirmation gates, no elicitation" as a design rule. The
send-truth plans of the current round (021, 025, 026) extend that passive
verifier; none reintroduce any client-interaction wait.

## Findings considered and rejected (2026-06-11, still standing)

- **Force-unwrap pattern in Send.swift / SendResolution.swift**
  (`text?.isEmpty == false ? text! : ...`): safe under the guard; style-only.
- **Session ID over plaintext HTTP**: by-design for a loopback-only
  transport; revisit only if network exposure becomes supported.
- **Missing HTTP authentication layer**: architectural, belongs to the
  Trustworthy Core track together with any deliberate network exposure.
- **`LIKE '%term%'` scans in search/find_chat**: FTS5 infeasible in place
  (chat.db is Apple's, read-only); sidecar index is a direction item.
- **Unstructured `Task` around the routing continuation** in HTTPTransport:
  pending-request timeout bounds the leak (plan 020 hardens adjacents).
- **SwiftLint/swift-format**: low value for a single-maintainer repo.
- **Inconsistent tool error patterns** (`Result` vs `throws`): fold into a
  future tool-layer consolidation (plan 023 narrows the practical harm).
- **FindChat migration onto ChatSummaryQueries**: batching win negligible at
  `targetCount ≤ ~5`; revisit only with reported latency.
